1. 이번 버전에서 다시 확인한 기준 문서
--------------------------------------

이번 점검에서는 docs 폴더의 다음 문서를 기준으로 현재 프로젝트 상태를 재확인했다.

- docs/planning/AI_건축_인허가_매니저.docx
- docs/planning/IA&wireframe.pdf
- docs/planning/AI_건축_인허가_매니저_프로토타입_요구사항.md
- docs/architecture/AI_건축_인허가_매니저_프로젝트_구조_설계안.txt
- docs/API_KEY_GUIDE.txt
- docs/history/R.E.D.v1.0.txt

v1.0에서 확정한 핵심 방향은 유지한다.

- 본 서비스는 단순 LLM 챗봇이 아니다.
- 주소 문자열이 아니라 PNU, 필지 Geometry, Parcel Profile, Building Profile, Action JSON을 기준으로 판단한다.
- 핵심 판단은 LLM이 아니라 룰엔진이 담당한다.
- RAG는 법령, 조례, 지구단위계획 근거를 Evidence Trace로 연결한다.
- LLM은 체크리스트, 사전협의 질문, 신청서 초안, 보고서 문장 생성 보조자로 제한한다.
- 최종 결과는 관할 행정청 판단을 대체하지 않는 사전진단 참고자료로 제공한다.

이번 v1.1의 핵심은 "회의용 mockup"을 "프로토타입 요구사항을 반영한 시연 가능 화면"으로 끌어올린 것이다.

2.5 지도 mockup 정리

- 기존 지도 mockup은 공간규제 레이어 패널과 PNU 말풍선이 지도 위에 겹쳐 어지러워 보였다.
- ParcelMapMock에서 지도 위 오버레이를 줄이고, 레이어 및 PNU 정보는 지도 하단 chip 형태로 분리했다.
- 지도는 필지, 도로, 구역, 핀 정도만 보여주는 조용한 시각 요소로 정리했다.
- 위치 입력 화면과 홈 화면 모두에서 지도 정보가 덜 겹치도록 개선했다.

2.8 EvidencePanel 탭 구조 추가

- 기존 근거 패널은 단순 목록 수준이었다.
- v1.1에서는 EvidencePanel을 탭형 구조로 변경했다.
  - 법령/조례 근거
  - Evidence Trace
  - Rule Trace
- Rule Trace에는 Rule ID, Rule 이름, 입력 필드, 결과, 판단 사유를 표시한다.
- Evidence Trace에는 절차명, 근거 문서, chunkId, 판단 사유, confidence를 표시한다.
- 프로토타입에서도 "왜 이런 결과가 나왔는지"를 확인할 수 있게 되었다.

2.9 대안 시나리오 화면 개선

- AlternativeScenarioPage에 현재 판단 요약, 유사 인허가 사례, 대안 비교를 강화했다.
- 사용자가 지적한 "권장 다음 행동" 영역을 구체화했다.
- 현재 권장 흐름은 다음처럼 표시된다.
  1) 주차계획 보완안 선택

  3) 건축과 제출자료 후보 반영
- 대안은 확정 승인 가능성을 의미하지 않고, 보고서 반영 및 사전협의 질문 생성으로 이어지는 보조 의사결정 자료로 표현했다.

3. 현재까지 된 것
----------------

현재 프로젝트는 다음 상태다.

- 기획서, IA, 구조 설계안, 프로토타입 요구사항이 프로젝트 구조와 프론트 화면에 반영되어 있다.
- 프론트엔드는 단순 mockup을 넘어, 시연 가능한 프로토타입 수준으로 개선되었다.
- 4단계 Wizard와 3-1 대안 시나리오 구조가 화면상 명확해졌다.
- 공공데이터, 룰엔진, RAG, Trace, LLM 산출물 생성의 개념이 화면에 드러난다.
- README는 팀 공유용 실행 문서로 일반화되었다.
- 백엔드는 endpoint 구조와 파일 경계가 잡힌 스캐폴딩 단계다.
- 인프라 구성 파일은 유지되고 있다.
  - PostgreSQL/PostGIS
  - Redis
  - Qdrant
- API 키 신청 가이드는 docs/API_KEY_GUIDE.txt에 정리되어 있다.
- 룰엔진, RAG, LLM, 문서 생성 서비스는 아직 대부분 pass 또는 스텁 상태다.

5) 샘플 필지 기반 Parcel Profile을 생성한다.
6) Action JSON schema를 확정한다.
7) 조건부 절차 3개만 우선 판별하는 최소 룰엔진을 만든다.
   - 용도변경
   - 개발행위허가
   - 농지전용
8) 샘플 법령 chunk 기반 Evidence Trace를 만든다.
9) 진단 결과 화면을 실제 API 응답으로 교체한다.
10) 체크리스트 생성 mock을 실제 로직으로 전환한다.
11) 보고서 HTML/DOCX 생성을 붙인다.

cd apps/web

접속:

8. 중요한 주의사항
-----------------

- .env는 Git에 올리지 않는다.
- API 키는 프론트엔드 .env에 넣지 않는다.
- API 키 값은 문서나 히스토리에 기록하지 않는다.
- LLM이 인허가 가능/불가를 직접 판단하게 만들지 않는다.
- 법령 설명은 반드시 Evidence Trace와 연결되도록 설계한다.
- Rule Trace와 Evidence Trace는 MVP 초기부터 저장 구조를 잡는 것이 좋다.
- 정보 부족, API 실패, 조례 최신성 미확인 상황에서는 단정하지 않고 추가정보 필요 또는 관할부서 확인 필요로 표시한다.
- 대안 시나리오는 승인 가능성 보장이 아니라 의사결정 보조와 사전협의 준비 자료로 표현한다.
