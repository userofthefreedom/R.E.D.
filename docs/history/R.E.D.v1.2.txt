R.E.D.v1.2
==========

작성일: 2026-05-29
프로젝트: AI 건축 인허가 매니저
팀: R.E.D. (Real Estate Developer)


1. 이번 버전에서 다시 확인한 기준 문서
--------------------------------------

이번 점검에서는 다음 문서를 기준으로 현재 프로젝트 상태를 재확인했다.

- docs/planning/AI_건축_인허가_매니저.docx
- docs/planning/IA&wireframe.pdf
- docs/planning/AI_건축_인허가_매니저_프로토타입_요구사항.md
- docs/architecture/AI_건축_인허가_매니저_프로젝트_구조_설계안.txt
- docs/api/API_KEY_GUIDE.txt
- docs/history/R.E.D.v1.1.txt

v1.1에서 확정한 핵심 방향은 유지한다.

- 본 서비스는 단순 LLM 챗봇이 아니다.
- 주소 문자열이 아니라 PNU, 필지 Geometry, Parcel Profile, Building Profile, Action JSON을 기준으로 판단한다.
- 핵심 판단은 LLM이 아니라 룰엔진이 담당한다.
- RAG는 법령, 조례, 지구단위계획 근거를 Evidence Trace로 연결한다.
- LLM은 체크리스트, 사전협의 질문, 신청서 초안, 보고서 문장 생성 보조자로 제한한다.
- 최종 결과는 관할 행정청 판단을 대체하지 않는 사전진단 참고자료로 제공한다.

이번 v1.2의 핵심은 "화면 중심 프로토타입" 위에 "백엔드 DB/API 기초 구조"와 "현재 상태 기준 문서"를 얹은 것이다.


2. v1.1 대비 달라진 점
----------------------

2.1 화면 캡처용 프론트 레이아웃 정리

- 와이드 웹 화면을 전체 캡처했을 때 과하게 비어 보이던 영역을 줄였다.
- 주요 화면의 카드 높이, 정보 밀도, 하단 공간, 우측 패널 배치를 조정했다.
- 대상 화면은 다음 흐름을 포함한다.
  - 홈
  - 프로젝트 대시보드
  - 내 프로젝트 목록
  - 새 진단 시작
  - 진단 Wizard 1~4단계
  - 대안 시나리오
  - 프로젝트 상세
  - 진단 이력/버전 비교
  - 보고서 미리보기
  - 지원/예외 안내
  - 데이터 출처 및 면책 안내
- 전체 화면 캡처 산출물을 프로젝트 루트의 capture/ 폴더에 저장했다.

2.2 백엔드 의존성 보강

- apps/api/pyproject.toml에 DB 계층 구현에 필요한 의존성을 추가했다.
  - SQLAlchemy 2.x
  - psycopg 3
  - Alembic
- FastAPI 백엔드가 단순 endpoint 스텁에서 DB 연결을 전제로 한 구조로 한 단계 이동했다.

2.3 DB base/session 구성

- apps/api/app/db/base.py를 SQLAlchemy Declarative Base 기준으로 정리했다.
- 공통 mixin을 추가했다.
  - IdMixin
  - TimestampMixin
- UUID 기반 id 생성 구조를 잡았다.
- naming convention을 둬서 향후 Alembic migration의 제약조건 이름이 안정적으로 생성되도록 했다.
- apps/api/app/db/session.py에서 settings.database_url 기반 engine, SessionLocal, get_session을 구성했다.

2.4 SQLAlchemy 모델 구현

- v1.1에서는 DB 모델이 대부분 pass 상태였으나, v1.2에서는 핵심 모델을 실제 SQLAlchemy 모델로 전환했다.
- 현재 구성된 주요 모델은 다음과 같다.
  - User
  - Project
  - Parcel
  - Building
  - RegulationOverlay
  - Action
  - DiagnosisRun
  - DiagnosisResult
  - ProcedureResult
  - RequiredDocument
  - LegalDocument
  - EvidenceChunk
  - EvidenceTrace
  - RuleSet
  - Rule
  - RuleExecutionTrace
  - Report
- app.models.__init__에서 전체 모델을 import하도록 정리했다.

2.5 Project 중심 ERD 보강

- Project는 사용자 프로젝트의 중심 테이블이다.
- Project에 owner_id를 추가하여 User와 연결할 수 있게 했다.
- 이 구조는 향후 JWT 인증과 프로젝트 단위 접근 제어를 붙이기 위한 기반이다.
- Project는 다음 엔티티와 연결된다.
  - Parcel
  - Building
  - RegulationOverlay
  - Action
  - DiagnosisRun
  - Report

2.6 RegulationOverlay 모델 추가

- 기획서에서는 공간규제 중첩 결과를 중요한 판단 입력으로 다룬다.
- 이를 Parcel JSON 내부에만 넣지 않고 별도 RegulationOverlay 모델로 분리했다.
- 저장 대상은 다음과 같다.
  - layer_code
  - layer_name
  - regulation_type
  - jurisdiction
  - overlap_area
  - overlap_ratio
  - source_name
  - source_url
  - data_base_date
  - collected_at
  - raw_payload
- 이 모델은 향후 PostGIS 공간 중첩, VWorld WMS/WFS 결과, 공간규제 레이어 판단의 저장 지점이 된다.

----------------

현재 프로젝트는 다음 상태다.

- 기획서의 5개 대표 화면은 현재 화면 구조상 "4단계 Wizard + 대안 시나리오 서브 페이지"로 표현되어 있다.
- 와이드 화면 캡처 기준으로 주요 화면의 빈 공간과 정보 밀도를 조정했다.
- capture/ 폴더에 전체 화면 캡처 산출물이 있다.
- 백엔드는 FastAPI router 구조가 잡혀 있다.
- SQLAlchemy 모델, DB session, repository/service의 기초 구조가 잡혔다.
- Project 기본 CRUD는 DB 연결 구조로 구현되어 있다.
- Parcel, Building, Action, RegulationOverlay 기본 create/list endpoint가 구현되어 있다.
- Project Dashboard / Project List / New Diagnosis / Diagnosis Wizard 일부 흐름이 Project API와 하위 리소스 API를 1차 호출한다.
- Diagnosis Wizard 1단계 지도는 실제 지도 타일 위에 mock 필지 오버레이를 표시한다.
- Alembic initial schema revision이 생성되었고 PostgreSQL/PostGIS에 적용되었다.
- PostgreSQL/PostGIS, Redis, Qdrant docker-compose 구성은 유지되고 있다.
- data/rules에는 v0.1 룰셋 YAML이 존재한다.
- data/legal-docs에는 raw, parsed, chunks, metadata 구조가 있다.
- services 폴더에는 location, public-data, rule-engine, rag, llm, document-generator 모듈 경계가 잡혀 있다.
- API 키 신청 가이드는 docs/api/API_KEY_GUIDE.txt에 정리되어 있다.
- README와 architecture 문서는 현재 상태 기준으로 업데이트되었다.

8. 중요한 주의사항
-----------------

- .env는 Git에 올리지 않는다.
- API 키는 프론트엔드 .env에 넣지 않는다.
- API 키 값은 문서나 히스토리에 기록하지 않는다.
- LLM이 인허가 가능/불가를 직접 판단하게 만들지 않는다.
- 법령 설명은 반드시 Evidence Trace와 연결되도록 설계한다.
- Rule Trace와 Evidence Trace는 MVP 초기부터 저장 구조를 잡는다.
- 정보 부족, API 실패, 조례 최신성 미확인 상황에서는 단정하지 않고 추가정보 필요 또는 관할부서 확인 필요로 표시한다.
- 대안 시나리오는 승인 가능성 보장이 아니라 의사결정 보조와 사전협의 준비 자료로 표현한다.
- Alembic revision 생성 전에는 모델 변경 사항을 한 번 더 확인한다.
- 마이그레이션 적용 전후로 Base.metadata와 실제 DB schema가 일치하는지 확인한다.
- capture/ 폴더는 화면 검토 산출물이므로 실제 제품 런타임 코드와 구분한다.
