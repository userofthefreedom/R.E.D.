AI 건축 인허가 매니저 프로젝트 폴더/파일 구조 설계안
=====================================================

작성 목적
---------
본 문서는 「AI 건축 인허가 매니저」 프로젝트를 설계하고 개발하기 위한 폴더 및 파일 구조를 정리한 것이다.
초기에는 추천 설계안이었으나, 현재는 실제 repo 구현 상태를 함께 반영하는 기준 문서로 사용한다.

본 프로젝트는 단순한 LLM 챗봇이 아니라, 다음 요소가 결합된 AI 웹 서비스이다.

- 위치 기반 필지 식별
- PNU 및 필지 Polygon 처리
- 건축물대장/토지이용계획/VWorld 등 공공데이터 연계
- 사용자 건축 행위 입력의 Action JSON 정규화
- 룰엔진 기반 인허가 절차 판단
- RAG 기반 법령·조례·지구단위계획 근거 검색
- Evidence Trace / Rule Trace 기반 근거 추적
- LLM 기반 체크리스트, 사전협의 질문, 보고서 생성
- DOCX/PDF 실무 산출물 생성

따라서 프로젝트는 프론트엔드, 백엔드, 공공데이터, 룰엔진, RAG, LLM, 문서 생성 모듈을 명확히 분리하는 모노레포 구조로 설계하는 것이 적절하다.


현재 반영 상태
---------------

2026-05-29 기준 현재 repo는 다음 상태이다.

- apps/web: Vue 3 + TypeScript + Vite 기반 화면 구현, OpenLayers 실제 지도 클릭/선택 UX, Action JSON state 연결, Rule Trace 표시
- apps/api: FastAPI 라우터, SQLAlchemy 모델, DB session, repository/service, Project 및 대상지 프로파일 기본 CRUD, DiagnosisRun/result 최소 흐름 구성
- apps/api/app/db/migrations: Alembic initial schema revision 생성 및 DB upgrade 검증 완료
- services: location, public-data, rule-engine, rag, llm, document-generator 폴더와 초기 스텁 구성
- data: rules, legal-docs/raw, parsed, chunks, metadata, seed, samples 구조 구성
- docs/api: API 키 신청 가이드 위치로 사용
- capture: 발표/PPT 삽입용 화면 캡처 산출물 저장

아직 구현 전이거나 mock/stub 상태인 영역은 다음과 같다.

- VWorld 역지오코딩은 1차 연결되었고, 지적도 geometry/PNU 정밀 변환은 추가 안정화 필요
- 건축HUB, 토지이용계획, 국가법령정보 API 실연동
- DiagnosisRun 생성/status/result 최소 흐름은 구현되었고, 비동기 실행 및 DB trace 저장은 추가 구현 필요
- 최소 Rule Engine 실행 결과와 Rule Trace API 응답은 구현되었고, YAML 기반 RuleLoader/DB 저장은 추가 구현 필요
- RAG 검색, Evidence Trace 저장, Qdrant 인덱싱
- LLM 기반 체크리스트/질문/보고서 생성과 DOCX/PDF 변환

설계 의도
---------
이 프로젝트는 일반 CRUD 서비스가 아니라 판단 파이프라인이 핵심인 서비스이다.
따라서 백엔드 내부에 모든 기능을 몰아넣기보다, 도메인별 서비스 모듈을 분리해야 한다.

핵심 분리 기준은 다음과 같다.

- apps/web: 사용자 화면
- apps/api: API 오케스트레이션
- services/location: 위치/PNU/공간정보 처리
- services/public-data: 공공 API 연계
- services/rule-engine: 명시적 조건 판단
- services/rag: 법령 근거 검색
- services/llm: 사용자 친화적 문서 생성
- services/document-generator: DOCX/PDF 생성
- data/rules: 버전 관리 가능한 룰셋
- data/legal-docs: RAG 대상 문서


2. 프론트엔드 구조: apps/web
---------------------------

기획서 기준 대표 화면은 다음 5개로 구성된다.

1. 위치 입력 및 PNU 변환
2. 건축 계획 입력 및 Action JSON 정규화
3. 판정 결과 및 근거 확인
4. 대안 시나리오 탐색
5. 실무 산출물 생성

현재 프론트 mockup에서는 진단 Wizard를 4단계로 구성하고, 대안 시나리오 탐색은
3단계 판정 결과 화면에서 진입하는 별도 route로 분리했다.
즉, 기획서의 5개 대표 화면을 화면 구조상 "4단계 Wizard + 대안 서브 페이지"로 표현한다.

따라서 프론트엔드는 글로벌/공통 화면, 프로젝트 대시보드, 4단계 진단 플로우,
대안 시나리오 서브 페이지, 산출물/보고서 화면을 분리한다.

프론트엔드 설계 포인트
---------------------
- 기획서의 5개 대표 화면을 기준으로 하되, 현재 mockup은 4단계 Wizard와 대안 시나리오 서브 페이지로 표현한다.
- 대안 시나리오는 결과 화면에서 조건부로 분기되는 별도 route로 둔다.
- 글로벌/공통 화면은 홈, 로그인, 회원가입, 마이페이지, 알림, 고객지원, 서비스 소개, 데이터 출처 안내로 분리한다.
- 프로젝트 영역은 대시보드, 내 프로젝트 목록, 프로젝트 상세, 저장된 보고서, 진단 이력/버전 비교를 포함한다.
- features 기준으로 나누면 화면 단위와 Use Case 단위가 일치한다.
- 지도 관련 컴포넌트는 components/map에 분리한다.
- 현재 지도 화면은 OpenLayers 지도 타일 위에서 클릭 좌표를 Location Resolve API로 전달하고, VWorld 역지오코딩 결과 또는 fallback 후보를 선택 상태로 반영한다.
- 지도 polygon은 VWorld 지적도 geometry가 오면 실제 geometry를 그리고, 없으면 클릭 좌표 주변 prototype polygon으로 fallback한다.
- Evidence Trace, 법령 근거, 절차 판단 결과는 재사용 가능성이 높으므로 components/evidence에 둔다.
- Pinia 또는 Vue Store는 프로젝트 상태, Wizard 진행 상태, 인증 상태로 분리한다.
- API 파일은 도메인 단위로 나누어 유지보수성을 확보한다.

백엔드 설계 포인트
-----------------
- diagnosis_orchestrator.py가 전체 진단 흐름을 조율한다.
- models는 DB 테이블 구조, schemas는 API 입출력 DTO로 분리한다.
- clients에는 외부 API 호출 코드를 둔다.
- repositories는 DB 접근 로직을 담당한다.
- services는 비즈니스 로직을 담당한다.
- workers는 장시간 작업, 비동기 작업, 문서 생성 작업을 담당한다.
- 현재 Project CRUD는 SQLAlchemy repository/service를 통해 DB와 연결되어 있다.
- 현재 Parcel, Building, Action, RegulationOverlay 기본 create/list endpoint가 Project 하위에 구성되어 있다.
- Alembic initial schema revision f5879b1bd8bb가 생성되었고 PostgreSQL/PostGIS에 적용 검증되었다.

서비스별 역할
------------

1) services/location
- 주소, 지번, 좌표, 지도 클릭 입력을 처리한다.
- 표준주소, 법정동코드, 본번, 부번, PNU, 필지 Polygon으로 변환한다.
- 좌표계 변환과 필지 Geometry 처리를 담당한다.

2) services/public-data
- 건축물대장, 건축HUB, 토지이용계획, VWorld, 공간규제 레이어를 호출한다.
- Parcel Profile과 Building Profile을 구성한다.
- 데이터 수집 시각, 기준일자, 캐시 사용 여부를 관리한다.

3) services/rule-engine
- 명시적 조건 판단을 수행한다.
- 건축허가, 건축신고, 용도변경, 대수선, 개발행위허가, 농지전용, 산지전용, 경관심의, 교통영향평가 등의 절차를 판별한다.
- Rule Trace를 생성한다.
- RAG 검색을 위한 Evidence Query를 생성한다.

4) services/rag
- 법령, 조례, 지구단위계획, 별표, 서식을 청킹한다.
- Dense 검색, BM25 검색, Hybrid 검색, Reranking을 수행한다.
- 절차 판단 결과에 연결할 EvidenceChunk를 선택한다.

5) services/llm
- LLM을 판단자로 사용하지 않고 설명자 및 문서 생성자로 제한한다.
- 체크리스트, 사전협의 질문, 대안 시나리오 설명, 보고서 문장을 생성한다.
- Structured Output 또는 JSON mode를 활용해 형식 안정성을 확보한다.

6) services/document-generator
- DOCX/PDF 산출물을 생성한다.
- 보고서 템플릿, 체크리스트 템플릿, 신청서 초안 템플릿을 관리한다.

핵심 모델 개념
--------------

1) Project
- 하나의 대상지에 대한 사전검토 단위이다.
- Parcel, Building, Action, DiagnosisResult와 연결된다.
- 현재 모델은 owner_id를 통해 User와 연결할 수 있게 구성되어 있다.

2) Parcel
- PNU, 법정동코드, 지목, 면적, 필지 Polygon, 용도지역·지구·구역, 기준일자와 수집 시각을 저장한다.

3) Building
- 기존 건축물의 주용도, 세부용도, 연면적, 층수, 구조, 사용승인일, 인허가 이력을 저장한다.

4) RegulationOverlay
- 필지 Polygon과 공간규제 레이어의 중첩 결과를 저장한다.
- layer_code, layer_name, regulation_type, jurisdiction, overlap_area, overlap_ratio, source, 기준일자, 수집 시각을 남긴다.

5) Action
- 사용자의 건축 계획을 법률 판단 가능한 Action JSON으로 정규화한 데이터이다.

6) DiagnosisRun
- 한 번의 진단 실행 단위이다.
- API 조회 시각, 모델 버전, 룰셋 버전, 법령 기준일자 등을 기록한다.

7) DiagnosisResult
- 프로젝트 단위의 종합 판단 결과이다.
- 주 인허가 유형, 가능성 수준, 리스크 등급, 판단 요약, 추가정보 필요 여부를 담는다.

8) ProcedureResult
- 절차별 판단 결과이다.
- 용도변경, 개발행위허가, 농지전용, 산지전용, 경관심의 등 절차별 대상 여부와 사유를 저장한다.

9) RequiredDocument
- ProcedureResult에 연결되는 절차별 필요서류 후보를 저장한다.

10) LegalDocument
- 법령, 조례, 지구단위계획 PDF, 별표, 서식 등 원문 문서 정보이다.

11) EvidenceChunk
- LegalDocument를 조문, 항, 호, 별표, 페이지, 표 단위로 나눈 검색 가능한 근거 조각이다.

12) EvidenceTrace
- 특정 ProcedureResult가 어떤 EvidenceChunk와 연결되는지 기록한다.

13) RuleSet / Rule / RuleExecutionTrace
- 적용된 룰셋 버전, 개별 룰, 실행 조건, 결과를 기록한다.

14) Report
- 진단 결과를 바탕으로 생성된 보고서 버전, 파일 경로, report context JSON, 면책 문구를 저장한다.


6. 룰셋 파일 구조
----------------

룰은 코드에 직접 작성하지 말고 데이터 파일로 관리하는 것이 좋다.
법령 개정, 조례 변경, 조건 수정이 발생할 수 있기 때문이다.

data/rules/
├── v0.1/
│   ├── main_permit.yaml
│   ├── building_report.yaml
│   ├── change_of_use.yaml
│   ├── development_activity.yaml
│   ├── farmland_conversion.yaml
│   ├── forest_conversion.yaml
│   ├── landscape_review.yaml
│   ├── traffic_impact.yaml
│   ├── sewage_consultation.yaml
│   └── education_environment.yaml
│
├── v0.2/
│   └── ...
│
└── rule_index.yaml


룰 예시
-------

rule_id: DEV-ACT-001
procedure_type: development_activity_permit
name: 지목 및 형질변경 기반 개발행위허가 검토
version: 0.1.0
conditions:
  all:
    - field: action.has_land_shape_change
      operator: equals
      value: true
    - field: parcel.land_category
      operator: in
      value: ["전", "답", "임야"]
result:
  target: true
  risk_level: caution
  reason: 성토·절토 또는 토지 형질변경 가능성이 있어 개발행위허가 검토가 필요합니다.
evidence_queries:
  - 개발행위허가 토지 형질변경 국토계획법
  - 개발행위허가 대상 성토 절토


룰 설계 원칙
------------
- 동일 입력에 대해 동일 결과가 나오도록 한다.
- 모든 룰 실행 결과는 RuleExecutionTrace로 남긴다.
- 룰셋은 버전별로 관리한다.
- 판단 결과에는 Evidence Query가 연결되어야 한다.
- LLM이 임의로 절차를 추가하지 않도록 룰엔진 결과를 기준으로 한다.


7. RAG 문서 구조
---------------

법령·조례·지구단위계획은 원문 파일만 보관하면 안 된다.
원문 → 파싱 → 청킹 → 메타데이터 생성 → 벡터 인덱싱 흐름이 필요하다.

data/legal-docs/
├── raw/
│   ├── national_laws/
│   ├── local_ordinances/
│   ├── district_unit_plans/
│   └── forms/
│
├── parsed/
│   ├── national_laws/
│   ├── local_ordinances/
│   └── district_unit_plans/
│
├── chunks/
│   ├── building_act_chunks.jsonl
│   ├── national_land_planning_act_chunks.jsonl
│   ├── farmland_act_chunks.jsonl
│   └── local_ordinance_chunks.jsonl
│
└── metadata/
    ├── document_registry.json
    └── source_versions.json


RAG 설계 원칙
-------------
- 법령 문서는 전문 단위가 아니라 조문·항·호·별표·서식 단위로 청킹한다.
- 지구단위계획 PDF는 페이지, 표, 별표 단위 근거 추적이 가능해야 한다.
- 각 chunk에는 문서명, 조문번호, 시행일, 수집일, 적용지역, URL, 페이지 번호 등을 저장한다.
- Dense 검색과 BM25 검색을 병행한다.
- Reranker는 전체 문서가 아니라 상위 후보군에만 적용한다.
- 최종 선택된 근거는 EvidenceTrace로 저장한다.

API 설계 포인트
---------------
- 진단은 시간이 오래 걸릴 수 있으므로 diagnosis run을 생성하는 방식이 적합하다.
- status API 또는 SSE/WebSocket으로 진행률을 제공한다.
- result, evidence, trace를 분리해서 결과와 근거를 독립적으로 조회할 수 있게 한다.
- alternatives는 result에서 고위험/저가능성 조건이 확인될 때 호출되는 보조 조회로 둔다.
- 보고서 생성은 진단 완료 후 별도 API로 분리한다.
- 현재 구현 기준으로 Project create/list/get/update는 DB와 연결되어 있고, Project 하위 리소스와 DiagnosisRun/result 일부 흐름도 DB/API와 연결되어 있다.
- Project 하위 Parcel, Building, Action, RegulationOverlay create/list도 DB와 연결되어 있다.
- 프론트 Wizard는 단계 이동 시 Parcel, RegulationOverlay, Action을 실제 API에 저장하고, DiagnosisRun 생성 후 최소 룰엔진 결과를 조회한다.
- /api/v1/diagnosis/runs/{run_id}/result는 저장된 Parcel/Action을 기반으로 조건부 절차, 누락정보, Rule Trace를 반환한다.
- 인증 라우터는 존재하지만 실제 JWT 발급/검증과 Project owner 접근 제어 연결은 다음 작업이다.

11. 최종 설계 요약

→ services/location, public-data, rule-engine, rag, llm, document-generator

→ infra/docker, db

이 구조의 핵심 장점은 다음과 같다.

- 기획서의 핵심 파이프라인을 코드 구조에 그대로 반영할 수 있다.
- 프론트엔드, 백엔드, AI, 룰엔진, RAG, 문서생성 역할을 분리할 수 있다.
- 팀 협업이 쉬워진다.
- MVP 범위를 단계적으로 줄이기 쉽다.
- 발표 시 “단순 챗봇이 아니라 판단 가능한 데이터 파이프라인”이라는 메시지를 명확히 전달할 수 있다.
- Rule Trace와 Evidence Trace를 통해 신뢰성과 설명 가능성을 확보할 수 있다.
